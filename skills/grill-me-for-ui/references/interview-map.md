# UI Interview Map

本文件帮助 Agent 选择下一条最有价值的问题分支。它不是要按顺序念完的问卷。

## 使用原则

- 先解决上游决策，再进入下游细节；
- 只询问会改变设计、视觉方向或验收结果的事项；
- 如果已有代码、截图或文档能回答，先检查证据；
- 每次只选择一个尚未解决的节点；
- 一个分支确认后，记录它对后续节点的约束；
- 视觉偏好与功能需求冲突时，明确展示冲突，不替用户悄悄取舍。

## 0. 任务分类与设计风险

| 类型 | 优先分支 | 常见风险 | 默认审美自由度 |
|---|---|---|---|
| 新产品或多页面应用 | 用户、范围、页面地图、设计系统 | 过早进入视觉细节 | 中等 |
| 单页面新设计 | 主要任务、内容层级、布局、状态 | 页面漂亮但任务不清 | 取决于页面类型 |
| 现有 UI 重设计 | 保留项、痛点、证据、迁移边界 | 只换皮或功能回归 | 先审计后决定 |
| Dashboard / 后台 | 数据任务、筛选、密度、表格、详情 | Card 堆砌、不可扫读 | 低至中 |
| 落地页 / 官网 | 受众、承诺、CTA、证据、品牌记忆 | 通用 SaaS 模板 | 中至高 |
| Portfolio / 创意展示 | 内容主角、叙事、节奏、动效 | 表现压过作品 | 高，但需克制 |
| 表单 / 多步流程 | 输入、验证、保存、恢复、完成状态 | 只设计正常提交 | 低至中 |
| 内容 / 文档页 | 阅读、目录、搜索、长内容 | 排版层级失控 | 中等 |
| 消费型移动端 | 高频任务、触感、状态、单手操作 | 展示效果妨碍长期使用 | 中等 |
| 独立组件 | 使用场景、变体、内容边界、状态 | 不可复用或状态缺失 | 受系统约束 |
| 设计系统 | Token、组件关系、例外治理 | 规则过度或缺乏一致性 | 系统级决定 |

### 先判断四个风险信号

- 使用频率；
- 错误代价；
- 信任与可解释要求；
- 品牌记忆的重要程度。

高频、高错误代价和高信任要求会降低实验自由度。品牌表达重要并不自动意味着需要更多动画。

## 1. 问题、用户与主要结果

### 必须得到的答案

- 谁是主要用户；
- 用户进入界面时要完成什么；
- 最重要的一个结果或动作；
- 当前方案失败在哪里，或新方案为什么需要存在。

### 可用问题

- 用户完成这页后，最重要的变化是什么？
- 如果只能保留一个主要动作，应该是哪一个？
- 这是给新手、熟练用户，还是两者都要兼顾？
- 当前最影响使用的，是找不到入口、看不懂信息、操作太慢，还是不信任结果？

### 依赖

没有明确主要任务前，不决定布局、CTA 强度和视觉表达度。

## 2. 范围、非目标与成功标准

### 必须得到的答案

- 本次包含哪些页面、流程或组件；
- 哪些功能、品牌资产或视觉规则必须保留；
- 是否允许改变信息架构、交互和视觉；
- 怎样判断重设计有效。

### 可用问题

- 本次只解决当前页面，还是允许调整前后页面的流程？
- 现有功能和品牌资产中哪些必须原样保留？
- 最重要的成功标准是完成率、速度、错误率、理解度、转化率还是主观质感？
- 若时间不足，哪些内容或视觉增强可以推迟？

## 3. 内容、数据与信息层级

### 必须得到的答案

- 页面必须展示的内容；
- 用户第一眼、第二眼和按需查看的信息；
- 数据量、长度、真实性和更新频率；
- 内容是否允许编辑、筛选、比较、分享或导出。

### 可用问题

- 用户第一眼必须看到哪一项信息？
- 哪些信息可以折叠、放到详情页或 Drawer？
- 页面面对的是几条数据、几十条还是上万条？
- 用户更常扫描、比较、搜索，还是逐条阅读？
- 标题、名称或翻译后文字最长可能到什么程度？
- 哪些指标、评价、客户或案例有真实来源，哪些只能使用 Placeholder？

### 典型方向

- 少量同类对象：List 或有真实分组意义的 Card；
- 多字段比较：Table；
- 单个对象详情：分区详情或 Descriptions；
- 核心指标概览：Statistic，但不能代替完整数据；
- 大量次级内容：Tabs、Collapse 或分层导航。

## 4. 页面地图、导航与核心流程

### 必须得到的答案

- 用户从哪里进入；
- 完成任务需要经过哪些页面或状态；
- 主导航与局部导航如何分工；
- 成功、失败和返回路径。

### 可用问题

- 用户通常从首页、搜索结果、通知还是外部链接进入？
- 这项任务应该在一页内完成，还是拆成步骤？
- 用户中断后，下次需要从哪里继续？
- 返回上一级时，筛选、滚动位置和未保存内容是否保留？
- 深层页面是否需要 Breadcrumb？

### 导航判断

- 少量顶级区域：Top Nav；
- 功能多且频繁切换：Sidebar；
- 长内容单页：Anchor 或 Sticky TOC；
- 明确顺序流程：Steps；
- 大量结果：Pagination 或虚拟滚动，由数据规模决定。

## 5. 布局与响应式结构

### 必须得到的答案

- 页面主布局和视觉重心；
- 内容最大宽度和密度；
- 桌面与移动端的优先级；
- 小屏下哪些内容重排、折叠、横向滚动或延后。

### 可用问题

- 这页更像操作工作台、阅读页，还是品牌叙事页面？
- 用户需要同时看到导航、列表和详情吗？
- 宽屏是利用空间展示更多信息，还是保持窄栏提高阅读性？
- 手机端最核心的一个动作是什么？
- 桌面表格在手机上应横向滚动、减少列、转摘要，还是进入详情？
- 页面是否需要一个明显的非对称构图，还是稳定对齐更适合任务？

### 常见布局

- Top Nav：公开站点或顶级栏目较少；
- Sidebar：后台、工具和高频多模块切换；
- Single Page：线性叙事或简单营销页；
- Doc Layout：长文档、目录和页面内导航；
- Grid：同类对象浏览或视觉叙事；
- Centered Column：阅读、写作和简单表单；
- Split View：列表与详情需要同时可见。

布局名称不是默认答案。根据任务、内容和视觉主张决定。

## 6. 组件与交互选择

### 判断顺序

1. 用户要完成的动作；
2. 数据和内容结构；
3. 状态与错误恢复；
4. 设计系统约束；
5. 最后才是组件外观。

### 可用问题

- 这是立即生效的设置，还是需要统一保存？
- 选项是互斥、可多选，还是从大量候选中搜索？
- 查看详情时需要保留列表上下文吗？
- 删除或提交是否可撤销？
- 次级信息是悬停解释、点击展开，还是永久可见？
- Card 是否表达真实分组或层级，还是仅为了让页面看起来丰富？

### 典型映射

- 二元立即生效：Switch；
- 互斥少量选项：Radio 或 Segmented；
- 多选：Checkbox；
- 大量候选：Select 或 AutoComplete；
- 保留背景上下文的详情：Drawer；
- 阻塞性短任务：Modal；
- 邻近轻量确认：Popconfirm；
- 非阻塞结果反馈：Toast；
- 持续重要信息：Alert。

## 7. 状态与恢复

### 对每个关键动作检查

- 初始、加载、空、局部加载和部分失败；
- 输入验证、网络失败和重试；
- 成功反馈；
- 无权限、只读和禁用；
- 破坏性操作确认、撤销或恢复；
- 重复点击和并发提交；
- 离开页面时的未保存内容。

### 可用问题

- 用户等待超过一秒时，需要看到进度、Skeleton 还是局部占位？
- 没有数据时，用户下一步应该做什么？
- 保存失败后，输入内容是否必须保留？
- 成功后是留在原地、显示 Result、进入详情还是返回列表？
- 删除是不可逆、软删除还是支持撤销？

## 8. Design Read 与审美校准

详见 `taste-calibration.md`。

### 必须得到的答案

- 界面类型、受众、任务和信任约束；
- 视觉主张；
- `EXPRESSION`、`MOTION`、`DENSITY` 的方向或区间；
- 一个主要标志性设计动作，或明确不需要；
- 最可能出现的模板化风险。

### 可用问题

- 这页更应像稳定高效的工具，还是具有明显品牌记忆的展示界面？
- 用户第一眼应先感到可信和清楚，还是新鲜和有冲击力？
- 参考页面中真正想借的是构图、排版、密度、颜色还是动效？
- 视觉重点主要靠排版和留白，还是靠图像和材质？
- 当前页面最像通用 AI 模板的地方是什么？
- 若只能保留一个视觉记忆点，它应该来自构图、排版、图像、材质还是交互？

### 不要直接问

- 你喜欢什么颜色？
- 你想要什么字体？
- 你要几分高级感？
- 要不要 Bento / Glassmorphism？

除非这些问题已经被上游证据缩小为真实取舍。

## 9. 视觉系统：排版、颜色、形状与深度

### 必须明确

- 排版角色与层级，而非只选一个字体名；
- 中性色、品牌色、强调色和语义色职责；
- 圆角、边框、阴影、透明度和表面层级规则；
- 图像、插画、图标和图表的视觉语言；
- 深色模式或高对比模式边界；
- 明确避免的项目特定模式。

### 可用问题

- 层级主要靠字号和留白，还是颜色和表面容器？
- 品牌色用于主要动作、品牌识别，还是大面积背景？
- 页面需要“边框和秩序”还是“表面和深度”来分层？
- 当前是否拥有足够质量的实拍、插画或产品图支持图像主导设计？
- 数字、代码或医学指标是否需要独立 Mono 角色？

### 原则

- 不做跨场景字体禁令；
- 不把大圆角、毛玻璃、阴影或纯黑自动等同于好坏；
- 同一页面的形状和表面应有一致规则；
- 设计选择必须能解释它服务的内容、任务或品牌作用。

## 10. 微交互和动效

### 必须明确

- Hover、Active、Focus、Disabled；
- 页面或内容切换是否需要 Transition；
- 加载和状态变化是否需要动画；
- 是否支持 reduced motion；
- 动画是否会延迟操作、遮挡信息或消耗性能。

### 原则

- 状态变化需要反馈；
- 动画服务于因果关系和空间关系；
- 高频操作应快速稳定；
- 持续循环动画不是默认高级感；
- 动效强度必须与 Design Read 和用户场景一致。

## 11. 可访问性、本地化与内容弹性

### 检查项

- 键盘顺序和 Focus 可见性；
- Label、错误提示和辅助文本；
- 颜色之外的状态表达；
- 点击目标尺寸；
- 图标按钮名称；
- 对比度；
- 长文本、200% 缩放和多语言；
- 表格和图表的替代信息；
- Skip Link 或页面内导航是否必要；
- reduced motion、reduced transparency 或高对比需求。

### 只在会改变方案时提问

- 是否必须满足特定法规或组织级无障碍标准？
- 是否支持中英双语、从右到左语言或超长医学术语？
- 是否面向老年人、低视力用户或只能键盘操作的环境？

## 12. 技术和设计系统约束

优先自行检查：

- React、Vue、Next.js 等框架；
- Tailwind、CSS Modules 等样式方案；
- shadcn/ui、Ant Design、MUI 等组件库；
- 现有 Token、主题和 `DESIGN.md`；
- 数据接口、权限和实时更新机制；
- 浏览器和设备范围；
- 性能、包体积、SSR 和动画限制。

只询问项目证据无法回答的选择：

- 是否允许引入新组件库或动效依赖；
- 是否必须兼容旧浏览器或低性能设备；
- 是否允许改变现有 Token；
- 是否需要输出持久 `DESIGN.md`。

## 13. 验收与交付

### 必须得到的答案

- 关键视口；
- 主要流程的成功和失败路径；
- 内容增长与真实数据边界；
- 视觉一致性和辨识度的可观察标准；
- UI Brief 是否足够，或还需要 `DESIGN.md`、实现提示词、Figma 或代码。

### 可用验收问题

- 隐去 Logo 后，页面是否仍与产品和用户任务相关？
- 第一眼重点是否唯一？
- 标志性设计动作是否清晰但不妨碍任务？
- 同一角色的颜色、形状、组件和 CTA 是否一致？
- 是否存在未经确认的假数据、假客户或装饰性区块？
- 移动端是否保留核心任务，而不是机械压缩桌面端？

## 分支优先级

当多个问题都未解决时，优先选择：

1. 下游影响最大；
2. 当前不确定性最高；
3. 错误决定返工成本最高；
4. 必须由用户而非 Agent 判断。

若剩余问题只影响低风险实现细节，停止访谈并将其记录为暂定默认。
