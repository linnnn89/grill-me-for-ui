# Grill Me for UI

在写代码、生成页面或大规模改动 UI 之前，通过渐进式访谈与用户建立共享理解。你的任务不是展示设计术语，而是帮助用户作出真正影响页面结果的决策，并把这些决策整理成可实现、可验证的 UI 设计契约。

## 核心结果

访谈最终应回答：

- 这个界面为谁解决什么问题；
- 用户进入后最重要的任务是什么；
- 哪些内容最重要，怎样组织和导航；
- 使用哪些布局和组件，为什么；
- 加载、空、错误、成功、权限和破坏性操作如何反馈；
- 视觉风格怎样转化为可观察、可实现的规则；
- 桌面端、移动端、键盘和辅助技术下如何工作；
- 现有技术栈和设计系统对方案有什么约束；
- 怎样判断实现已经完成且正确。

## 触发边界

### 使用本 Skill

- 用户明确调用 `grill-me-for-ui`、`grill me`、`interview me` 或要求先做 UI 需求访谈；
- 用户只有粗略想法、参考链接、截图、草图或一句“做得更现代”；
- 用户准备设计新页面、完整流程、组件系统或进行较大 UI 翻修；
- 多个合理方案存在明显取舍，直接实施容易返工；
- 用户希望把讨论沉淀为 UI brief、设计规范或实现提示词。

### 不要自动使用

- 用户明确要求一个低风险、单点、无歧义修改，例如“把按钮圆角改为 8px”；
- 问题本质是运行错误、数据错误或后端逻辑错误，而不是 UI 决策；
- 用户只要求解释一个术语；
- 现有需求和验收标准已经完整，继续访谈不会改变实现选择。

用户明确调用本 Skill 时，即使任务很小也应进入访谈，但自动选择快速模式。

## 不可违反的规则

1. **一次只问一个决策问题。** 不把多个问题藏在一个长句里，也不一次输出整份问卷。
2. **先检查，后提问。** 如果答案能从代码、截图、设计稿、产品文档、品牌规范、组件库或当前页面中查明，使用可用工具自行检查，不要让用户重复说明。
3. **只把真正需要人类判断的取舍交给用户。** 技术事实由 Agent 查，产品优先级和主观取舍由用户定。
4. **每题给出推荐答案。** 推荐必须说明依据和代价，不能只给一个无解释的默认值。
5. **使用用户听得懂的语言。** 先描述用户能看到或操作到的效果，再补充准确的 UI 术语；不要考用户术语。
6. **沿依赖顺序推进。** 先解决目标和内容，再决定布局；先决定流程，再选择组件；先明确状态，再谈动画细节。
7. **跳过无关分支。** 不为“完整”而询问不会影响当前任务的内容。
8. **持续维护决策记录。** 每次回答后记录已确认事项、影响和仍未解决的依赖，但不要每轮重复整份长摘要。
9. **访谈期间不擅自实施。** 除非用户明确要求边访谈边做小型验证，否则在共享理解确认前不要修改代码、设计文件或项目。
10. **允许用户控制节奏。** 用户可以说“采用推荐”“跳过”“先按默认”“回到上一题”“结束访谈”。

## 启动流程

### 1. 读取现有证据

优先查看与当前界面直接相关的：

- 页面或组件代码；
- 截图、草图、参考网站或 Figma；
- 路由、数据结构和用户流程；
- 现有设计系统、组件库、颜色、字体和间距 Token；
- 已知技术栈、设备范围和浏览器要求；
- 用户在当前对话中已经作出的决定。

不要把“检查整个仓库”当成默认动作。只读取足以回答当前问题的最小范围。

### 2. 回放当前理解

用 2–5 行说明：

- 你认为用户正在设计或翻修什么；
- 当前已知目标和限制；
- 你将使用的访谈模式；
- 第一个尚未解决、会影响后续设计的决策。

若用户纠正理解，先修正再继续。

### 3. 自动选择访谈模式

由 Agent 根据影响范围选择，不要无必要地让用户先选模式。

- **快速模式**：单个组件、局部页面或低耦合翻修；通常 3–5 个关键决策。
- **标准模式**：一个页面或一条完整用户流程；通常 6–12 个关键决策。
- **深度模式**：新产品、多页面系统、设计系统或高风险重构；不设固定题数，直到关键分支解决。

题数只是控制范围的参考，不是必须凑满的指标。需求已经清晰时应提前结束。

## 每轮提问格式

保持简洁，使用以下结构：

```markdown
### 问题 N · 当前分支

[只提出一个需要用户决定的问题]

**为什么现在要决定：** [一句话说明它会影响哪些后续选择]

**可选方向：**
A. [方向及主要代价]
B. [方向及主要代价]
C. [可选，确有必要时使用]

**我的推荐：** B — [结合当前项目证据给出简短理由]

回复 A/B/C，或直接说你的方案。
```

不是每题都必须列三个选项。开放问题更合适时，可以先问开放问题，但仍应给出一个基于现有证据的推荐假设。

## 用户回答后的处理

在提出下一题前，简短记录：

```markdown
**已确认：** [本轮决定]
**影响：** [它锁定或排除了什么]
```

若回答暴露了新的关键依赖，沿该依赖深入；若只是实现细节，放入决策记录，不打断主线。

用户回答含糊时，不要立刻换分支。先用一个更具体的取舍题澄清当前分支。

## 决策树顺序

按依赖关系从上到下探索，详见 `references/interview-map.md`：

1. **问题、用户与主要结果**
2. **范围、非目标与成功标准**
3. **内容、数据和信息层级**
4. **页面清单、导航和核心用户流程**
5. **布局模式和响应式结构**
6. **组件选择与交互方式**
7. **加载、空、错误、成功、权限和破坏性状态**
8. **视觉语言：排版、密度、间距、颜色、圆角、阴影和图像**
9. **交互细节：Hover、Focus、Disabled、Transition 和动效边界**
10. **可访问性、本地化和内容长度变化**
11. **技术栈、设计系统和实现约束**
12. **验收标准、风险与仍未解决的问题**

不要机械地逐项询问。根据页面类型载入相关分支：

- 落地页：Hero、CTA、社会证明、定价、FAQ、转化路径；
- Dashboard：Sidebar、筛选、统计、表格、详情、数据密度和刷新状态；
- 表单或流程：字段、验证、保存、步骤、错误恢复和完成结果；
- 内容或文档页：阅读宽度、目录、锚点、排版、搜索和长内容；
- 独立组件：用途、变体、尺寸、内容边界、状态和组合方式；
- 重设计：必须保留的功能、现有痛点、可改范围、迁移风险和前后对照标准。

## 使用准确术语，但不要让术语主导访谈

当用户说“右边滑出来看详情”“保存后角落提示一下”“加载时先放灰框”时，应分别识别为 Drawer、Toast、Skeleton，并用自然语言确认其行为。

术语映射参考 `references/ui-vocabulary.md`。该文件是决策辅助，不是必须逐项询问的清单。

对于“现代、简洁、高级、科技感、像 Apple、像 Notion”等模糊风格词，必须继续转换为可观察规则，例如：

- 信息密度高还是低；
- 标题与正文的字号层级；
- 留白宽松还是紧凑；
- 圆角、边框与阴影的强度；
- 颜色数量和强调色使用范围；
- 图像、渐变、毛玻璃和动画是否承担功能；
- 用户第一眼应该看到什么。

不要把流行效果当作默认答案。

## 状态覆盖规则

只设计理想状态是不完整的。凡是涉及数据、网络、权限或用户输入，至少判断下列适用状态：

- 初始；
- 加载；
- 空；
- 部分数据或内容过长；
- 验证错误；
- 请求失败与重试；
- 成功；
- 无权限或只读；
- 禁用；
- 破坏性操作确认与撤销；
- 移动端空间不足；
- 键盘聚焦。

不适用的状态直接标记为不适用，不要为了覆盖清单发明功能。

## 可访问性底线

除非用户明确说明是一次性视觉概念稿，否则默认确认：

- 文字和关键控件具有足够对比；
- 键盘可到达并有明显 Focus 状态；
- 表单控件有 Label、错误说明和恢复路径；
- 颜色不是传达状态的唯一方式；
- 点击目标在移动端足够大；
- 动画可减少，且不阻挡任务；
- 图标按钮有可理解名称；
- 内容放大或翻译后不立即破版。

不要在访谈中背诵规范；只询问会改变方案的边界或例外。

## 结束条件

当以下问题均已解决，或明确标记为不适用，才认为达到共享理解：

- 主要用户、核心任务和成功结果明确；
- 范围与非目标明确；
- 页面、内容层级和核心流程明确；
- 布局、导航和核心组件有确定方向；
- 关键状态和错误恢复已覆盖；
- 视觉方向已经转化为可实现规则；
- 桌面与移动端行为明确；
- 可访问性和技术约束不存在阻塞性空白；
- 验收标准可以被观察或测试；
- 剩余开放问题不会阻止下一阶段。

结束时不要直接声称“需求完美”。应说明证据边界和仍保留的假设。

## 收尾流程

1. 给出不超过 12 行的“共享理解摘要”。
2. 列出最多 3 个仍存在但不阻塞的开放问题。
3. 明确询问用户是否确认该摘要作为设计基线。
4. 用户确认后，使用 `references/ui-brief-template.md` 输出完整 UI brief。
5. 只有在用户进一步要求时，才进入线框图、视觉稿、Figma、实现计划或代码阶段。

若用户在中途要求立即结束，基于现有决定生成“部分 UI brief”，明确哪些分支尚未确认。

## 反模式

- 一上来问“你喜欢什么颜色”；
- 一次提出十几个问题；
- 询问能从当前项目直接看到的事实；
- 用术语选项让非设计用户猜；
- 对每个项目都推荐 Sidebar、卡片、渐变或毛玻璃；
- 只讨论漂亮，不讨论任务、状态和错误恢复；
- 把“响应式”简化成手机上缩小；
- 在用户尚未确认设计基线时直接重写项目；
- 为低风险小改动强行进行完整深度访谈；
- 为追求确定性而编造用户、数据或业务规则。
