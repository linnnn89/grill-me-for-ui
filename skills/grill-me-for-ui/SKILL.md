# Grill Me for UI

在写代码、生成页面或大规模改动 UI 之前，通过渐进式访谈与用户建立共享理解。你的任务不是展示设计术语，也不是把某套流行审美强加给所有项目，而是帮助用户作出会真正改变页面结果的决定，并把这些决定整理成可实现、可验证、可持续复用的设计契约。

## 核心结果

访谈最终应回答：

- 这个界面为谁解决什么问题；
- 用户进入后最重要的任务和结果是什么；
- 哪些内容最重要，怎样组织和导航；
- 使用哪些布局和组件，为什么；
- 加载、空、错误、成功、权限和破坏性操作如何反馈；
- 视觉方向如何从模糊形容词转化为清晰的设计语言；
- 设计应多克制、多有表现力、多密集，以及动效承担什么职责；
- 桌面端、移动端、键盘和辅助技术下如何工作；
- 现有技术栈和设计系统对方案有什么约束；
- 怎样判断实现不仅“能用”，而且具有一致、适合场景的视觉品质。

## 触发边界

### 使用本 Skill

- 用户明确调用 `grill-me-for-ui`、`grill me`、`interview me` 或要求先做 UI 需求访谈；
- 用户只有粗略想法、参考链接、截图、草图或一句“做得更现代 / 更高级”；
- 用户准备设计新页面、完整流程、组件系统或进行较大 UI 翻修；
- 多个合理方案在任务、信息层级或审美方向上存在明显取舍，直接实施容易返工；
- 用户希望把讨论沉淀为 UI brief、`DESIGN.md`、设计规范或实现提示词。

### 不要自动使用

- 用户明确要求一个低风险、单点、无歧义修改，例如“把按钮圆角改为 8px”；
- 问题本质是运行错误、数据错误或后端逻辑错误；
- 用户只要求解释一个术语；
- 现有需求、设计系统和验收标准已经完整，继续访谈不会改变实现选择。

用户明确调用本 Skill 时，即使任务很小也应进入访谈，但自动选择快速模式。

## 不可违反的规则

1. **一次只问一个决策问题。** 不把多个问题藏在一个长句里，也不一次输出整份问卷。
2. **先检查，后提问。** 如果答案能从代码、截图、设计稿、产品文档、品牌规范、组件库或当前页面中查明，使用可用工具自行检查。
3. **只把真正需要人类判断的取舍交给用户。** 技术事实由 Agent 查，产品优先级和主观取舍由用户定。
4. **每题给出推荐答案。** 推荐必须说明证据、收益与代价，不能只是无解释默认值。
5. **先描述可观察效果，再补充术语。** 不让非设计用户猜 Drawer、Bento、Editorial 等术语。
6. **沿依赖顺序推进。** 先目标和内容，再流程与布局；先视觉立场，再字体、颜色和动效细节。
7. **跳过无关分支。** 不为“完整”而询问不会改变当前方案的内容。
8. **持续维护决策记录。** 区分用户已确认、从证据推断和暂定默认值。
9. **访谈期间不擅自实施。** 除非用户明确要求边访谈边做小型验证，否则在设计基线确认前不改代码或设计文件。
10. **审美规则必须情境化。** 不把“不用 Inter”“禁止居中 Hero”“只能一个强调色”“必须持续动画”等外部 Skill 规则当成普遍真理。
11. **一个页面只需要一个主导视觉观点。** 其余设计决定服务于该观点，而不是堆叠流行效果。
12. **允许用户控制节奏。** 用户可以说“采用推荐”“跳过”“先按默认”“回到上一题”“结束访谈”。

## 启动流程

### 1. 读取最小必要证据

优先查看与当前界面直接相关的：

- 页面或组件代码；
- 截图、草图、参考网站或 Figma；
- 路由、数据结构和用户流程；
- 现有设计系统、组件库、颜色、字体和间距 Token；
- 已知技术栈、设备范围和浏览器要求；
- 用户在当前对话中已经作出的决定。

不要默认检查整个仓库。只读取足以判断当前设计分支的最小范围。

### 2. 判断界面类型与设计风险

先识别主要表面类型，因为不同表面需要不同的审美自由度：

- **产品 / 工作流 UI**：效率、反馈和稳定性优先；
- **Dashboard / 数据工具**：扫读、比较、密度和可信度优先；
- **营销页 / 官网 / Portfolio**：品牌记忆、叙事和转化优先；
- **内容 / Editorial**：阅读节奏、排版和内容气质优先；
- **消费型移动端**：触感、情绪和高频操作优先；
- **组件或设计系统**：一致性、组合能力和 Token 约束优先；
- **重设计**：先审计现有问题、保留项和迁移风险，再讨论新风格。

受监管、医疗、金融、公共服务、儿童、老年人或无障碍优先场景，会降低实验性设计的自由度，但不等于只能做成普通模板。

### 3. 输出 Design Read

在第一题前，用 2–5 行回放当前理解，并给出一条暂定的 Design Read：

```text
我将它理解为：[界面类型]，面向[主要用户]，核心任务是[任务]；
视觉上应偏向[气质 / 设计家族]，但受[信任、品牌、设备或可访问性约束]限制。
本次采用[快速 / 标准 / 深度]模式。
```

Design Read 是可修正假设，不是最终结论。若两个方向会导致显著不同结果，只问一个最高价值的对比问题；若证据已经充分，不要为了形式继续提问。

### 4. 自动选择访谈模式

- **快速模式**：单个组件、局部页面或低耦合翻修；通常 2–5 个关键决策。
- **标准模式**：一个页面或一条完整用户流程；通常 5–10 个关键决策。
- **深度模式**：新产品、多页面系统、设计系统或高风险重构；不设固定题数，直到关键分支解决。

题数只是范围参考。结束条件是剩余不确定性不再显著改变下一阶段，而不是凑够问题数量。

## 每轮提问格式

```markdown
### 问题 N · 当前分支

[只提出一个需要用户决定的问题]

**为什么现在要决定：** [它会影响哪些后续选择]

**可选方向：**
A. [方向，以及用户能看到的效果与主要代价]
B. [形成明确对比的方向，以及主要代价]
C. [确有第三种合理方向时使用]

**我的推荐：** B — [结合当前项目证据说明理由]

回复 A/B/C，或直接说你的方案。
```

开放问题更合适时可以使用开放问题，但仍应给出一个基于证据的暂定假设。审美问题优先使用具体对比，例如“严谨紧凑的工作台”与“宽松沉浸的展示页”，不要只让用户选择“现代 / 高级 / 科技感”。

## 用户回答后的处理

在提出下一题前简短记录：

```markdown
**已确认：** [本轮决定]
**影响：** [锁定、排除或延后的方向]
```

若回答暴露新的关键依赖，沿该依赖深入；若只是实现细节，写入决策记录，不打断主线。回答含糊时，先把当前分支改写成更具体的可观察取舍，不要直接跳到另一个主题。

## 决策树顺序

详见 `references/interview-map.md`。默认依赖顺序为：

1. 问题、用户与主要结果；
2. 范围、非目标与成功标准；
3. 内容、数据和信息层级；
4. 页面清单、导航和核心用户流程；
5. 布局模式和响应式结构；
6. 组件选择与交互方式；
7. 加载、空、错误、成功、权限和破坏性状态；
8. Design Read 与审美校准；
9. 排版、颜色、形状、深度、图像和图表；
10. Hover、Focus、Transition 和动效边界；
11. 可访问性、本地化和内容弹性；
12. 技术栈、设计系统和实现约束；
13. 验收标准、风险与交付格式。

不要机械逐项询问。根据页面类型载入相关分支。

## 审美校准

视觉分支使用 `references/taste-calibration.md`，核心包含以下五步。

### 1. 三项旋钮

由 Agent 根据 Design Read 先推断，不要默认要求用户报数字：

- **视觉表达度 `EXPRESSION`**：1 为高度克制和可预测，10 为强烈、实验性和高度差异化；
- **动效强度 `MOTION`**：1 为近乎静态，10 为动画主导的编排体验；
- **信息密度 `DENSITY`**：1 为画廊式宽松，10 为驾驶舱式高密度。

数字是沟通辅助，不是设计质量分数。只有当用户需要微调或两个方向难以区分时才展示具体值。

### 2. 视觉主张

将气质压缩为一句可执行的视觉主张：

```text
以[主导构图 / 排版 / 材质]建立[目标感受]，
用[一种强调方式]突出[核心信息或动作]，
避免[最可能出现的模板化倾向]。
```

### 3. 单一标志性动作

每个页面或流程最多确定一个主要记忆点，例如：

- 非对称 Hero 与内容留白；
- 数据表与详情之间连续的空间关系；
- 一套独特但稳定的排版节奏；
- 贯穿全页的图像裁切方式；
- 用一处有因果关系的动效解释状态变化。

标志性动作不是必须添加的特效。产品工作台可以把“极强的扫读秩序”本身作为记忆点。

### 4. 情境化 Anti-Slop 审核

主动检查，但不要机械禁止：

- 是否未经思考就使用 AI 紫色渐变、深色网格 Hero、三张等宽卡片和默认玻璃效果；
- 是否每个区块都用同一种 Card、Eyebrow 或左右交替布局；
- 是否用随机字体、圆角和阴影制造“丰富感”；
- 是否为了显得高级而牺牲任务效率、对比度或内容可信度；
- 是否生成未经用户提供的统计数字、客户名称、Logo 或社会证明；
- 是否存在与产品、受众和品牌无关的装饰性动效。

某个常见模式若适合当前场景，可以使用，但必须说明它为什么成立。

### 5. 设计系统落点

- 现有项目已有设计系统时，优先复用并明确允许偏离的范围；
- 选择成熟系统时，使用一个主系统，不混搭多个互相竞争的系统；
- 无现成系统时，至少明确颜色角色、排版层级、间距、圆角、深度与核心组件状态；
- 多页面、长期迭代或跨 Agent 项目，可在 UI Brief 后输出 `DESIGN.md`，格式参考 `references/design-md-template.md`。

## 参考设计的拆解方式

用户提供参考图或网站时，不问“要不要做得像它”。先拆解：

- 构图与信息层级；
- 信息密度与留白；
- 排版气质与字号节奏；
- 颜色角色和强调范围；
- 边框、阴影、透明度和材质；
- 图像、插画、图标或图表；
- 动效的因果关系和节奏；
- 哪些部分适合当前产品，哪些只适合原参考场景。

然后只询问最可能改变当前方向的一项借鉴取舍。

## 状态覆盖规则

凡涉及数据、网络、权限或用户输入，至少判断下列适用状态：

- 初始、加载、空、部分数据或内容过长；
- 验证错误、请求失败与重试、成功；
- 无权限、只读、禁用；
- 破坏性操作确认、撤销或恢复；
- 移动端空间不足和键盘聚焦。

不适用的状态直接标记为不适用，不为覆盖清单发明功能。

## 可访问性底线

除非用户明确说明是一次性视觉概念稿，否则默认确保：

- 文字和关键控件具有足够对比；
- 键盘可到达并有明显 Focus 状态；
- 表单控件有 Label、错误说明和恢复路径；
- 颜色不是传达状态的唯一方式；
- 点击目标在移动端足够大；
- 动画可减少，且不阻挡任务；
- 图标按钮有可理解名称；
- 内容放大、增长或翻译后不立即破版。

不要在访谈中背诵规范；只询问会改变方案的边界或例外。

## 结束条件

当以下问题已解决或明确标记为不适用，才认为达到共享理解：

- 主要用户、核心任务和成功结果明确；
- 范围与非目标明确；
- 页面、内容层级和核心流程明确；
- 布局、导航和核心组件有确定方向；
- 关键状态和错误恢复已覆盖；
- Design Read、三项旋钮和视觉主张明确；
- 标志性动作已确定或明确不需要；
- 审美方向已转化为排版、颜色、间距、形状、深度和图像规则；
- 桌面与移动端行为明确；
- 可访问性和技术约束不存在阻塞性空白；
- 验收标准可以被观察或测试；
- 剩余开放问题不会阻止下一阶段。

结束时不要声称“需求完美”。说明证据边界、默认假设和仍存在的风险。

## 收尾流程

1. 给出不超过 12 行的共享理解摘要。
2. 列出最多 3 个仍存在但不阻塞的开放问题。
3. 明确询问用户是否确认该摘要作为设计基线。
4. 用户确认后，使用 `references/ui-brief-template.md` 输出完整 UI Brief。
5. 对多页面、设计系统、重设计或预计跨会话迭代的项目，可同步生成 `DESIGN.md`；单点页面默认不额外制造文档。
6. 只有用户进一步要求时，才进入线框图、视觉稿、Figma、实现计划、提示词或代码阶段。

若用户中途结束，基于现有决定生成部分 UI Brief，并明确未确认分支。

## 反模式

- 一上来问颜色、字体或“喜欢什么风格”；
- 一次提出十几个问题；
- 询问能从当前项目直接看到的事实；
- 用术语选项让非设计用户猜；
- 对每个项目都推荐 Sidebar、Bento、渐变、毛玻璃或大圆角；
- 照搬外部审美 Skill 的绝对禁令，不考虑 Dashboard、医疗、公共服务等不同场景；
- 把高表现力误解为更多动画和更多视觉效果；
- 只讨论漂亮，不讨论任务、状态和错误恢复；
- 把响应式简化成手机上缩小；
- 在用户尚未确认设计基线时直接重写项目；
- 为低风险小改动强行进行深度访谈；
- 为页面填充感而编造用户、数据、客户、评价或业务规则。
